# 下一可交付版本需求与验收标准

> 文档状态：受控开发基线（Controlled Baseline）  
> 版本：v1.0  
> 建立日期：2026-09-08  
> 适用版本：下一可交付版本（vNext）  
> 责任人：产品方案、系统方案与开发实现由技术负责人统一负责  
> 用途：作为 vNext 范围控制、开发启动、测试验收和发布判断的受控基线索引

如本文与 `docs/development-roadmap-2026H2.md` 或其他旧计划冲突，以本文对 vNext 的范围与发布门槛为准；旧计划只保留历史背景作用。本文引用的 UI 基线、Learning 内容清单、权限矩阵、测试计划和发布证据在进入 Git 后成为本基线的受控组成部分。

## 1. 文档目的

本文件将下一可交付版本从方向性要求转化为可开发、可测试、可交付的工程要求。

vNext 必须同时解决四件事：

1. 完成达到团队体验和正式交付标准的玩家端 UI/UX 与计分体验；
2. 证明现有多租户系统可以支撑 10 多个组织、总计约 100 人并发操作；
3. 补齐运行可见性、异常降级、运营告警和交付保障；
4. 交付守望学习 Learning MVP 的产品框架、少量正式内容、权限和基础学习闭环。

本文同时明确不进入 vNext 的事项，避免在一个版本中继续扩大范围。

## 2. 背景与基线变化

### 2.1 已确认的业务要求

- 系统服务 10 多个组织，每个组织约十几至二十人；
- 总计约 100 人可能同时操作；
- 系统需要保持稳定，不能因集中使用而崩溃；
- 系统需要支持组织、角色和权限设置；
- 系统需要支持组织状态、账号有效期等时间相关设置；
- 正式交付包含生产部署；
- 后端接口或外部依赖不可用时，系统需要有明确的降级行为；
- 故障需要快速反馈到运营端。

### 2.2 当前项目已经具备的能力

以下现状基于 2026-09-08 对提交 `4fd628b` 的代码检查，仅用于确定开发起点，不替代 vNext 的回归和验收证据：

- 生产环境使用 PostgreSQL；
- Node.js + Express 服务统一提供 API、玩家端、组织管理端和运营管理端；
- 已有 `boss`、`operator`、`enterprise`、`watcher` 角色；
- 用户通过 `enterprise_id` 归属组织；
- 组织管理员接口已经使用组织条件限制数据范围；
- 组织成员统一跟随组织有效期，独立用户使用个人有效期；
- 账号或组织过期、停用后，受保护请求会在后端被拒绝；
- 已有单设备会话控制；
- PostgreSQL 已使用连接池，读取遇到部分瞬时连接错误时会有限重试；
- 已有 Zeabur 部署路径；
- TTS 的自动生成、缓存和播放已经完成。

### 2.3 本轮发生的计划变化

- 玩家端 UI/UX 初稿尚未达到可交付标准，2026-09-08 起按更完整的工作流重新设计；
- TTS 开发已经完成，vNext 只做回归验证，不再作为主开发任务；
- Learning 由远期完整项目调整为 vNext 必须交付的 MVP；
- 飞书数据同步、游戏性优化和品牌落地页延期，不进入 vNext；
- 原排期对 UI 完成度和 Learning 范围的假设已经失效，旧的 2026-09-30 待上线节点及 2026-10-16 正式上线节点不再自动视为承诺；
- vNext 日期必须在 UI 方案基线、技术拆分和第一轮性能基线完成后重新确认。

## 3. vNext 产品目标

vNext 的交付结果不是“功能已经写完”，而是：

- 玩家可以顺利完成登录、开局、游戏、计分、结算和复盘；
- 组织成员和组织管理员只能访问其权限与组织范围内的数据；
- 100 人集中操作时，核心链路保持稳定，数据不串号、不丢失、不重复；
- 发生服务异常时，用户知道发生了什么、哪些操作尚未保存、接下来应该怎么做；
- 运营人员能够在用户集中反馈之前发现故障并获得告警；
- Learning 已经形成可以继续填充课程内容的最小产品框架，而不是继续平铺卡牌；
- 部署、回滚、监控、告警和排障均有可执行说明。

## 4. 范围与优先级

### 4.1 发布阻断范围

## 5. 用户与系统边界

### 5.1 用户角色

| 角色 | vNext 权限边界 |
|---|---|
| `boss` | 平台级全部管理权限，管理组织、用户、系统设置和运营权限 |
| `operator` | 仅访问被授予的运营模块，不拥有平台级权限配置权 |
| `enterprise` | 仅管理自己所属组织的成员、活动、邀请码和场次数据 |
| `watcher` + `enterprise_id` | 使用所属组织授予的游戏权益，不具备组织管理权限；Learning 权益按 Gate 1 决策执行 |
| `watcher` + 无 `enterprise_id` | 使用个人账号有效期对应的游戏权益；Learning 权益按 Gate 1 决策执行 |

vNext 不新增会议纪要中的体验者、见习、认证、导师、城市合伙人完整商业角色模型。Learning 的免费/付费访问只建立可扩展的权益边界，不在本轮完成全部商业等级迁移。

### 5.2 数据源与真实性

- 用户、组织、权限、账号有效期、课程权限和学习进度以 PostgreSQL 为最终事实来源；
- 前端缓存仅用于展示和故障恢复，不得成为最终事实来源；
- 客户端显示“已保存”前必须收到后端明确成功响应；
- 无法确认写入结果时，必须显示“待同步”或“保存失败”，不得假装成功；
- 所有时间判断以服务端时间为准，客户端时间只负责显示。

## 6. 功能需求与验收标准

### 6.1 玩家端 UI/UX 与计分体验

#### UI-001 设计基线

要求：

- vNext 开发必须基于一套冻结的页面结构、视觉规范和核心交互流程；
- 设计基线至少覆盖登录、首页、开局设置、游戏进行、反馈、计分、阶段切换、暂停/恢复、结束、复盘入口、个人中心和 Learning 入口；
- 颜色、字体、间距、按钮状态、弹窗、错误提示和加载状态形成一致规则；
- 在设计基线确认前，不以零散页面修改代替整体 UI/UX 完成。

验收：

- 核心页面均有可评审的最终界面；
- 同类组件行为和视觉一致；
- 不存在仍以临时样式、占位文案或开发按钮呈现的核心流程；
- 设计基线变更必须同步更新本文件或对应设计说明。

#### UI-002 核心游戏闭环

要求：玩家可以完整完成以下流程：

1. 登录或使用已有会话进入系统；
2. 完成必要的个人资料；
3. 选择游戏模式、卡牌组、参与者和活动信息；
4. 开始游戏并逐张完成卡牌选择；
5. 查看每次选择的反馈和伍力变化；
6. 正确完成阶段切换、暂停和恢复；
7. 正常通关或提前结束；
8. 查看最终得分并进入复盘。

验收：

- 每一步均有明确的当前状态、成功反馈和失败反馈；
- 重复点击不会重复开局、重复计分、重复结算或重复写入；
- 游戏结束后继续体验卡牌不会继续计分、写历史或回传正式游戏事件；
- 刷新和短暂离开页面不会无提示丢失进行中的本地进度；
- 多个浏览器标签页的游戏场次互不覆盖；
- 最后一张卡牌仍然展示选择反馈；
- 阶段顺序和卡牌数量以本局配置为准，不使用硬编码阶段顺序。

#### UI-003 响应式与兼容性

验收设备与环境：

- iOS Safari 在发布日最新与前一个主版本；
- Android 微信内置浏览器在发布日最新稳定版本；
- 桌面 Chrome 和 Edge 在发布日最新稳定版本；
- 手机宽度 360px 至 430px；
- 桌面宽度 1280px 及以上。

发布测试计划必须记录实际设备、操作系统、浏览器和微信版本。“短暂离开”按页面进入后台 5 分钟后恢复测试；弱网按下行 1.5 Mbps、上行 750 Kbps、往返延迟 150 ms、丢包率 1% 测试。

验收：

- 核心按钮不被遮挡；
- 页面不出现阻断操作的横向滚动；
- 弹窗可关闭、内容可滚动；
- 触控区域可稳定点击；
- 输入法弹起后仍可提交表单；
- 页面无阻断性控制台错误；
- 弱网下加载、超时和重试状态可见。

#### UI-004 可用性验收

- 团队体验必须使用统一测试地址和统一反馈入口；
- Emma、晓依完成一轮完整游戏和一轮异常路径测试；
- S0 问题清零后方可进入发布验收；
- S1 问题必须有修复结论或明确风险接受记录；
- 反馈不得只停留在聊天记录，必须进入版本问题清单并标记状态。

#### UI-005 基础无障碍

- 表单输入具有可读标签和错误说明；
- 纯图标按钮具有可读名称；
- 状态和错误不能只依赖颜色表达；
- 主要操作可以通过键盘完成并显示焦点位置；
- 正文与背景对比度不低于 4.5:1，大字号文字不低于 3:1；
- 用户启用“减少动态效果”时，欢迎动画和非必要动效被关闭或显著减弱。

验收使用 axe 规则自动扫描加人工键盘走查；核心页面的 `critical` 和 `serious` 级问题必须为 0。

### 6.2 TTS

#### TTS-001 状态

TTS 功能已经完成，不进入新的功能扩展。

#### TTS-002 回归验收

- 卡牌音频缺失时可以触发生成；
- 已生成音频能够缓存并复用；
- 播放、暂停和切换卡牌行为正确；
- 同一内容不会因重复请求产生无意义的重复生成；
- 音频生成或 OSS 不可用时，游戏主流程继续运行；
- 失败时向用户显示音频暂不可用，不阻断选牌和计分；
- 移动端自动播放限制不会导致页面卡死或无限重试。

### 6.3 多租户、权限与时间设置

#### TEN-001 组织数据隔离

以下数据必须受组织边界保护：

- 组织资料；
- 组织成员；
- 邀请码；
- 活动；
- 游戏场次；
- 成员统计；
- 活动统计；
- Learning 进度和后续组织学习统计。

验收：

- 建立至少 12 个组织和 200 个测试账号；
- 对所有包含组织、用户、活动、邀请码和场次 ID 的接口执行跨组织访问测试；
- 对带资源 ID 的跨组织读取、修改和删除统一返回 404，避免暴露资源是否存在；纯角色权限不足返回 403；
- 返回体、日志和错误信息不得泄漏其他组织数据；
- 并发压测期间不得出现任何跨组织串读或串写。

#### TEN-002 角色权限

- 普通用户不能调用组织管理和平台管理接口；
- 组织管理员不能调用平台级管理接口；
- `operator` 只能调用被分配模块对应的接口；
- `boss` 才能修改组织有效期、独立账号有效期和运营权限；
- 后端负责最终权限判断，前端菜单隐藏不能作为权限控制；
- 所有 `/api/admin/*`、`/api/enterprise/*` 写接口必须有明确角色守卫。

验收：

- 建立“角色 × 接口 × 操作”的权限矩阵；
- 权限矩阵中的拒绝项全部有自动化测试；
- 修改用户角色或权限后，后续请求按新权限执行；
- 已签发 JWT 中的旧角色信息不能绕过数据库中的最新权限状态。

#### TEN-003 组织成员上限

- `max_members` 是强约束；
- 检查剩余名额和加入组织必须处于同一数据库事务；
- 并发邀请注册、Boss 添加成员和组织管理员添加成员必须遵循同一配额规则；
- 失败请求不得创建半成品用户或消耗邀请码次数。

验收：

- 在仅剩 1 个名额时同时发起至少 10 个加入请求，最终只能有 1 个成功；
- 成员数永远不超过 `max_members`；
- 失败请求返回明确的配额错误；
- 数据库中不存在孤立账号、错误组织归属或错误邀请码计数。

#### TEN-004 邀请码并发使用

- 邀请码状态、到期时间、最大使用次数和当前使用次数必须在后端校验；
- 验证邀请码、创建账号、加入组织和增加使用次数必须作为一个原子操作完成；
- 并发使用最后一个名额时，只允许一个请求成功；
- 注册失败时不得消耗邀请码次数；
- 同一注册请求因超时重试时不得重复创建账号或重复消耗次数。

验收：

- 对仅剩 1 次的组织邀请码同时发起至少 10 个注册请求，最终只能有 1 个成功；
- `used_count` 与实际成功注册人数一致；
- 邀请码过期、停用或耗尽后均不能继续注册；
- 失败和重试后不存在半成品账号。

#### TIME-001 账号与组织有效期

- `boss`、`operator` 保持有效期豁免；
- 组织成员和组织管理员统一跟随组织状态及组织有效期；
- 独立用户使用个人有效期；
- `NULL`、永久、未来、到期和已过期状态必须区分；
- 组织停用或到期后，已登录账号的下一次受保护请求立即被拒绝；
- 全库继续使用毫秒级 Unix 时间戳；
- 管理端统一按北京时间展示。

验收：

- 覆盖到期前、到期时和到期后的边界测试；
- 覆盖组织停用、组织不存在、未开通、永久和个人过期；
- 前端提示与后端错误码一致；
- 客户端修改本地时间不能绕过有效期控制。

### 6.4 Learning MVP

#### LRN-001 产品框架

Learning MVP 建立三级结构：

1. 模块；
2. 课程；
3. 课时。

首版模块结构：

- 守望者准则；
- 理论体系与五大风险；
- 案例学习。

验收：

- 登录后可以从个人中心或主导航进入 Learning；
- 用户能够查看模块、课程、课时和完成状态；
- 尚未开放的内容明确显示未开放，不显示空白页或失效按钮；
- 课程结构不继续直接等同于 45 张卡牌平铺列表；
- 使用一条新增的测试课程数据验证：不修改 Learning 页面代码即可在现有模块中显示新课程和课时；该项属于 vNext 的扩展性检查，不承诺未来所有课程形态都无需改动。

#### LRN-002 首版内容

- vNext 至少包含 3 个正式课时；
- 三个首版模块各至少包含 1 个可完整学习的正式课时；
- “守望者准则”的首个正式课时标记为免费；
- 正式内容必须由团队提供或确认，开发过程不得自行生成并冒充已确认课程内容；
- 内容缺失时使用明确的待提供状态，不使用虚构正文填满页面。

#### LRN-003 免费与付费权限

- 课程和课时支持 `free` 与 `paid` 权限标记；
- 通过当前登录与账号有效性校验的用户可以访问免费内容；
- 付费内容只向具有 Learning 付费权益的用户开放；
- 无权限用户可以看到课程存在，但不能读取受限正文；
- 权限判断必须在后端执行；
- 账号有效期只决定账号能否使用系统，不能在未经业务确认时自动等同于 Learning 付费权益；
- Gate 1 必须确定 Learning 权益的事实来源，以及个人权益和组织权益之间的优先级；
- vNext 不实现支付、优惠和复杂商业等级联动。

#### LRN-004 学习进度

- 记录用户开始学习、完成课时和最近学习位置；
- 同一用户跨设备重新登录后可以恢复服务端已保存进度；
- 不同用户和不同组织之间的学习进度严格隔离；
- 重复提交完成操作不会重复累计；
- 运营端暂不要求完整学习分析；vNext 仅要求能够按用户、课程、课时和完成时间查询学习进度。

验收：

- 课时完成后刷新页面仍显示已完成；
- 退出并重新登录后进度仍存在；
- 重复点击完成不会产生多条完成记录；
- 用户不能读取或修改其他用户的进度。

#### LRN-005 基础测验

- 至少有一个课时测验；
- 支持单选或多选题、提交、得分和通过/未通过结果；
- 记录用户最近一次结果和最高结果；
- 重复提交不重复累计学习完成次数；
- vNext 测验结果不直接发放正式认证、证书或价格优惠。

### 6.5 运行可见性

#### OBS-001 健康检查

服务必须提供：

- 存活检查：确认 Node 进程能够响应；
- 就绪检查：确认应用已经初始化完成并可以接收流量；
- 数据库检查：确认 PostgreSQL 可以执行轻量查询；
- 卡牌数据源检查：确认游戏所需卡牌能够读取；
- 版本信息：返回当前发布版本和启动时间。

验收：

- 数据库不可用时，存活状态和就绪状态能够被区分；
- 未就绪实例不会被当成正常实例接收流量；
- 健康检查自身不执行重查询、不泄漏配置和密钥；
- 外部监控无需登录即可读取最小健康状态，详细状态仅运营角色可见。

#### OBS-002 结构化日志

每个 API 请求至少记录：

- 请求 ID；
- 时间；
- 方法与路由模板；
- 状态码；
- 总耗时；
- 用户 ID；
- 组织 ID；
- 错误类型；
- 当前发布版本。

日志不得记录：

- JWT；
- 密码；
- 验证码；
- 完整手机号；
- OSS 或第三方服务密钥；
- 完整敏感课程正文和用户反馈正文。

验收：

- 用户报告问题后，可以通过时间、用户和请求 ID 定位完整请求链路；
- 5xx 错误必须带统一错误码并在日志中保留堆栈；
- 返回给用户的错误不得包含数据库结构、SQL 或内部堆栈；
- 未处理的 Promise 拒绝和进程异常必须被记录并触发告警。

#### OBS-003 指标与运营状态

运营端至少能够查看：

- 服务当前状态；
- 数据库当前状态；
- 当前发布版本；
- 服务最近启动时间；
- 最近 5 分钟请求量和 5xx 错误率；
- 核心接口 P95 延迟；
- 活跃游戏场次数；
- 游戏事件写入失败数；
- 最近一次故障时间和恢复时间。

技术监控至少收集：

- Node CPU、内存和事件循环延迟；
- PostgreSQL 连接池总连接、空闲连接、等待请求和连接错误；
- 接口请求量、状态码和延迟分布；
- Bmob、OSS、LLM 和卡牌数据源调用失败数；
- 进程启动和重启次数。

指标口径：

- 核心接口指 `/api/me`、`/api/settings`、`/api/cards`、`/api/game/start`、`/api/game/event`、`/api/game/finish`、`/api/enterprise/dashboard` 和 `/api/enterprise/sessions`；
- 5xx 错误率按“窗口内 `/api/*` 的 5xx 响应数 ÷ `/api/*` 总响应数”计算，健康检查流量不计入分母；
- P95 按服务端记录的完整请求耗时计算，15 秒超时请求同时计入失败数；
- 活跃游戏场次指 `ended_at IS NULL` 且最近 15 分钟存在游戏事件的场次；
- 最近一次故障指最近 24 小时内触发过告警规则的事件；
- 请求与依赖指标至少保留 30 天，告警事件和发布记录至少保留 180 天。

#### OBS-004 告警

以下情况发送到指定运营飞书群：

- 服务连续 1 分钟不可用；
- 数据库连续两次 30 秒探测失败，即持续 1 分钟不可连接；
- 5xx 错误率连续 5 分钟超过 1%；
- 核心接口 P95 连续 5 分钟超过 2 秒；
- 1 分钟内游戏事件写入失败达到 5 次，或失败率超过 1%；
- Node 进程重启；
- 故障恢复。

告警必须包含：环境、版本、开始时间、故障类型、影响范围、当前状态和排查入口。

外部监控每 30 秒探测一次；达到规则后 2 分钟内必须送达运营。连续两次探测成功后判定恢复并发送恢复通知。主渠道为指定飞书群，次渠道为指定运营邮箱。监控平台必须具备自身探测失败提示；飞书发送失败时继续发送邮件，并在监控平台保留未送达状态。每次发布前真实触发一次告警和恢复通知。

### 6.6 异常降级与恢复

#### DEG-001 降级原则

- 降级不等于所有功能离线可用；
- 优先保证已经开始的游戏不因短暂网络故障立即丢失；
- 任何未确认写入的数据必须显示为未同步；
- 管理操作失败时保持只读，不允许前端制造成功假象；
- 外部非核心服务失败不得拖垮游戏、计分和结算主链路；
- 恢复后必须能够确认哪些数据已经同步、哪些仍需处理。

#### DEG-002 玩家端 API 故障

- 已加载的页面、卡牌和本局状态保留在当前标签页；
- 网络超时或 5xx 时显示全局服务异常状态；
- API 客户端统一以 15 秒无响应作为超时；
- 未同步游戏事件进入按用户、标签页和游戏场次隔离的本地待同步队列；
- 页面明确显示待同步数量；
- 同一场次的事件严格按原顺序单路重放，不并发打乱顺序；
- 网络错误、超时和 5xx 可以重试；除会话恢复流程外，4xx 不自动重试；
- 自动重试采用 1、2、4、8、15 秒退避，连续 5 次失败后停止自动重试并提供手动重试；
- 登录失效时暂停队列，重新登录为同一用户后才能继续；切换账号不得发送前一账号的数据；
- 永久失败事件保留错误码、请求 ID 和人工处理入口，不得阻塞查看其他已确认数据；
- 待同步数据同步成功后立即删除，未成功数据最多保留 24 小时，过期前向用户明确提示；
- 本地队列不得存储 JWT、密码、验证码和不必要的个人信息；
- 关闭页面前仍有未同步数据时必须明确警告用户；
- 登录、新开局和需要服务端授权的操作在离线时不得伪造成功。

验收：

- 页面进入后台 5 分钟后恢复，本局状态仍然正确；
- API 中断 2 分钟期间产生的事件在恢复后按顺序同步且不重复；
- 中断期间退出并登录另一账号，原账号事件不会被发送到新账号；
- 5 次重试仍失败时，页面停止重试并显示可操作的失败状态；
- 同步完成后，本地不再保留已同步事件；
- 服务端记录与客户端确认事件按事件 ID 完成最终对账。

#### DEG-003 写入幂等

- 游戏开始、游戏事件和游戏结算需要客户端请求标识；
- 后端和数据库必须能够识别重复请求；
- 同一请求因超时重发时只产生一次业务结果；
- 幂等约束由数据库保证，不能只依赖单进程内存；
- 幂等冲突必须返回原成功结果或明确的已处理状态。

验收：

- 对相同事件同时提交 10 次，数据库只保留 1 条业务事件；
- 服务写入成功但响应丢失后，客户端重试不会重复计分；
- 服务重启后幂等保证仍然成立。

#### DEG-004 外部依赖故障

| 依赖 | 降级要求 |
|---|---|
| OSS / TTS | 音频和图片不可用时继续游戏，显示资源不可用状态 |
| LLM / 生图 | 不阻断游戏结算；复盘显示延迟、失败或无插图版本 |
| Bmob 短信 | 停止新验证码登录，保留已登录会话，并立即告警 |
| 卡牌数据源 | 已开始游戏继续使用本局已加载快照；新开局停止并明确提示 |
| PostgreSQL | 停止所有需要确认写入的操作，保护本地待同步数据并告警 |

#### DEG-005 整体服务宕机

当前前端和 API 同属一个 Node 服务，因此服务完全宕机后不能依靠应用自身通知运营，也不能依靠该服务返回降级页面。

vNext 必须补充：

- 独立于 Node 进程的外部健康探测；
- 独立于 Node 进程的运营告警；
- 平台级或独立静态托管的维护页；
- 服务恢复通知。

### 6.7 性能与稳定性

#### PERF-001 负载模型

性能验证使用以下内部工程口径：

- 12 个组织；
- 至少 200 个测试账号；
- 至少 10,000 个历史游戏场次和 150,000 条游戏事件，用于验证数据增长后的查询表现；
- 120 个并发用户持续 30 分钟；
- 150 个并发用户持续 5 分钟峰值测试；
- 流量覆盖获取用户信息、读取设置、读取卡牌、开始游戏、提交卡牌事件、结束游戏、读取组织看板和读取场次列表；
- 短信验证码不进入高并发压测，避免对真实计费服务制造流量；
- 使用预置账号和已签发测试会话完成鉴权流量。

120 并发是在已确认的 100 人业务规模上保留 20% 内部工程余量。压测必须在资源规格、数据库版本和网络路径接近生产的测试环境执行，不直接向正式短信、LLM 和 OSS 计费接口制造负载。

并发用户构成：

- 75% 执行游戏链路：读取用户和设置、读取一次卡牌、开始一局、以 8 至 15 秒思考时间提交 15 次事件、结束一局；
- 15% 执行个人中心和 Learning 读取；
- 5% 执行组织看板、成员与场次列表读取；
- 5% 执行不调用真实短信服务的已认证登录态恢复和资料读取。

测试先预热 5 分钟，再进入 30 分钟稳态；峰值测试另行升至 150 并发并持续 5 分钟。每次请求超过 15 秒按超时失败处理。全局 5xx 错误率按“全部 API 的 5xx 响应数 ÷ 全部 API 请求数”计算；核心接口 5xx 错误率按“核心接口的 5xx 响应数 ÷ 核心接口请求数”计算。主动取消和脚本自身错误单独列出，不得从结果中静默删除。

#### PERF-002 通过标准

- Node 进程不退出；
- 全局 5xx 错误率低于 1%；
- 核心接口 5xx 错误率低于 1%；
- 核心接口 P95 响应时间不超过 2 秒；
- 读取卡牌和设置的接口 P95 不超过 1 秒；
- 数据库连接池不存在持续耗尽；
- 无跨组织数据泄漏；
- 无游戏场次、事件或结算数据丢失；
- 无重复计分和重复游戏事件；
- 测试结束后数据库记录数与压测请求预期一致；
- 性能报告记录环境配置、数据规模、脚本版本、结果和瓶颈。

数据对账至少比较：成功开局请求数与新增场次数、每局确认事件数与唯一事件数、成功结算请求数与已结束场次数、各组织预期数据量与实际数据量。任何无法解释的差异均判定为失败。

以上为当前规模的内部发布线，不构成商业 SLA。商业 SLA 需要在真实使用数据形成后单独决定。

### 6.8 架构约束与待定实现

已经确定且实现不得绕开的约束：

- PostgreSQL 是用户、租户、权限、游戏和 Learning 数据的最终事实来源；
- 权限必须由后端基于当前数据库状态判断；
- 写请求幂等必须跨进程重启成立，并由持久化唯一性保证；
- 整体服务故障的探测和告警必须独立于 Node 进程；
- 非核心外部服务失败不得阻断游戏计分与结算。

Gate 1 决定、本文暂不锁定的实现：

- 本地待同步队列使用的浏览器存储机制；
- 幂等键的字段、表结构和接口兼容方式；
- 指标采集、展示和外部监控服务；
- 独立维护页的托管位置；
- Learning 付费权益的数据模型与管理入口；
- 性能问题出现后采用索引、查询优化、缓存、连接池调整还是实例扩容。

待定实现必须满足前述验收标准。选择具体技术时需要记录它解决的当前问题、增加的运行复杂度和回退方式，不为未出现的规模提前引入微服务或分布式基础设施。

## 7. 安全与数据要求

### SEC-001 API 边界

- 所有敏感数据和写接口默认要求认证；
- 所有管理接口必须在后端校验角色；
- 所有组织接口必须在后端校验当前用户的实时组织归属；
- 不信任 JWT 中缓存的角色和组织信息作为唯一判断依据；
- ID 参数必须校验资源归属；
- 前端隐藏按钮不能替代授权。

### SEC-002 输入与输出

- 所有写接口校验必填字段、类型、长度和允许值；
- 上传继续受文件大小和类型限制；
- API 错误统一返回稳定错误码；
- 生产响应不得返回 SQL、堆栈和密钥；
- 日志和运营页面默认对手机号等个人信息脱敏。

### SEC-003 数据变更

- 数据库结构变更必须有迁移脚本；
- 迁移脚本必须能够在测试环境重复验证；
- 破坏性迁移必须先备份并说明回滚方法；
- Learning 进度和游戏幂等数据需要唯一约束；
- 正式部署前必须完成一次备份恢复演练。

### SEC-004 生产管理端认证

- 生产环境的 `boss` 和 `operator` 登录不得只凭手机号签发令牌；
- 管理端统一使用密码和短信验证码完成身份验证，再校验角色；
- `DEV_KEY` 登录只能在明确的非生产环境启用；
- 生产环境禁用默认开发密钥和默认 JWT 密钥；
- 管理端登录、验证码和密码重置接口必须有限流和失败审计；
- 修改密码、停用账号或强制下线后，已有管理会话立即失效。

验收：

- 只提交已知手机号不能登录管理端；
- 生产环境调用开发登录接口被拒绝；
- 连续错误登录触发限流并留下脱敏审计记录；
- 被停用或强制下线的管理员不能继续使用旧令牌。

### SEC-005 恢复与回退目标

以下为 vNext 内部交付目标，不构成商业 SLA：

- 数据恢复点目标（RPO）不超过 1 小时，即发生数据库级灾难时最多丢失 1 小时数据；
- 服务恢复时间目标（RTO）不超过 2 小时，从确认故障开始计算到核心游戏链路恢复；
- 无数据库结构变化的应用版本回滚不超过 15 分钟；
- 带数据库迁移的发布必须保留新旧应用兼容窗口，迁移失败后 30 分钟内恢复上一可用版本；
- 迁移前必须创建可恢复备份，破坏性字段删除不得与首次应用发布同时执行；
- Gate 1 必须确认生产 PostgreSQL 的备份频率、保留周期和时间点恢复能力；无法满足目标时必须在继续开发前升级为发布决策。

验收：

- 使用生产同规格测试备份完成一次新数据库恢复；
- 恢复后核对用户、组织、游戏场次、游戏事件、Learning 进度和系统设置；
- 实际记录备份时间、恢复开始时间、恢复完成时间和数据缺口；
- 完成一次应用回滚和一次迁移失败回退演练。

## 8. 测试要求

### 8.1 自动化测试

必须具备：

- 权限矩阵测试；
- 跨租户越权测试；
- 有效期状态与时间边界测试；
- 组织人数并发配额测试；
- 游戏开始、事件、结算的幂等测试；
- Learning 权限和进度隔离测试；
- 核心 API 回归测试；
- 玩家端核心流程端到端测试；
- 组织管理端核心流程端到端测试；
- 运营管理端健康状态检查；
- 负载测试。

### 8.2 故障演练

发布前必须主动验证：

- PostgreSQL 断连 2 分钟后恢复；
- Node 服务重启；
- 请求写入成功但响应丢失；
- OSS/TTS 不可用；
- LLM/生图服务超时；
- 短信服务失败；
- 卡牌数据源不可用；
- 用户在存在未同步事件时刷新或关闭页面。

每次演练记录：触发方式、用户表现、运营告警、数据结果、恢复时间和遗留问题。

### 8.3 团队验收

团队验收至少包含：

- 一轮正常游戏闭环；
- 一轮提前结束与恢复；
- 一轮弱网或 API 失败；
- 一轮组织管理员操作；
- 一轮 Learning 学习与测验；
- 一轮移动端真实设备检查。

所有问题按以下等级记录：

| 等级 | 定义 | 发布规则 |
|---|---|---|
| S0 | 数据泄漏、无法开局、错误计分、数据丢失、系统崩溃、无法部署或回滚 | 必须清零 |
| S1 | 核心流程明显受阻、主要页面不可用、降级错误、学习进度错误 | 必须清零或经明确风险接受 |
| S2 | 非阻断体验问题、次要兼容问题 | 可带责任人和日期延期 |
| S3 | 文案、视觉微调和增强建议 | 进入后续版本池 |

缺陷豁免只针对已完成需求中的具体已知问题，不能用来删除或整体豁免第 4 节列出的必交范围。S1 风险接受必须由技术负责人写明影响和临时保护措施，并由产品验收人及发布批准人共同确认。

## 11. 开发顺序

| 顺序 | 工作流 | 关键产出 | 可并行条件 |

| 1 | UI/UX 方案冻结 | 页面结构、交互、视觉基线 | Learning 内容可由团队同时准备 |

## 13. 发布判定

满足以下全部条件才能称为“可交付版本”：

- Gate 0 至 Gate 4 全部通过；
- S0 问题为 0；
- S1 问题为 0，或存在明确责任人、影响说明和书面风险接受；
- 120 并发与 150 峰值测试通过；
- 跨租户测试零失败；
- 游戏写入幂等测试零失败；
- Learning 权限和进度隔离测试零失败；
- 外部告警和恢复通知经过真实触发；
- 部署、回滚和备份恢复均实际演练；
- 生产发布后完成登录、开局、事件、结算、组织管理、Learning 和告警检查。

只完成页面、只完成代码、只完成部署或只完成团队体验，均不等于通过本版本验收。

## 14. 变更控制

- 本文件合入后成为 vNext 开发基线；
- 新需求进入 vNext 前必须说明它替换哪项工作、增加多少时间和影响哪个阶段门；
- 发布阻断范围变化必须更新本文并提交 Git；
- 验收标准变化必须记录原因，不能在开发结束后为适配现状而降低标准；
- 延期项保持延期，除非经过明确优先级调整；
- 发布日期只在 Gate 1 完成后确认，不以未经拆分的总工期作为承诺。
