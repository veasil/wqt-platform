## 1. 更新目标与边界

让桌游端、组织管理端和平台管理端共同表达同一业务关系：**人登录，选择组织拥有的账号，再以该账号使用功能；个人资料属于人，角色、套餐和场次属于账号。**

本轮要解决登录、选账号、页面权限、历史展示和管理操作的语义差异，并清理旧流程中会写错对象的入口。沿用 HTML/JavaScript 与两套 Vue 3 前端，沿用现有视觉风格和导航结构，不借本轮更换框架或重做全部品牌视觉。

已确认且直接复用：账号唯一组织；一个人可绑定多个账号；多账号登录必须选择，单账号可直入；账号换绑不改变角色、期限、组织和场次；新使用者可看该账号全部历史，旧使用者失权；城市级管理员可读组织全部账号历史，不能改删他人场次；付费到期保留登录、历史与已有报告，拒绝新开局和新增收费处理，已开局可继续事件及结算；按人单设备、登录起固定24小时，切换不续期；免费组织ID为0。

非目标：微信、支付、升级/重复购买、身份自动合并、通用权限编辑器、跨前端自动单点登录、自动运营、生产部署和迁移。管理员任命与管理员账号换绑保护、同一人换号的具体核验、活动申请细节等仍待确认，暂不开放对应写入口。

## 3. 三端共有的登录与账号上下文

### 登录与选择

流程：手机号+密码+短信 → 身份认证 → 账号选择 → 刷新当前账号与能力 → 进入对应页面。

- 账号选择卡片显示账号名/ID、组织名、角色、套餐、到期状态；免费组织显示“免费组织”，不显示“无组织”。
- 只有一个账号时使用后端已选择结果；多个账号不凭上次选择自动绕过本次选择。没有可用账号时展示原因、刷新与退出入口，不循环跳回登录。
- 桌游端展示全部当前有效绑定账号；组织端提示哪些账号是城市级管理员；平台端提示哪些是boss。非管理账号可选择后返回桌游端，但不能进入管理业务页面。
- 顶栏持续展示“当前账号 · 所属组织”，个人姓名作为使用者信息单独展示。管理权限来自当前所选账号，而不是这个人是否还绑定另一个管理员账号。
- 切换成功才替换token、账号状态及缓存；失败保留原状态。切换后清理旧组织列表、筛选、详情及弹窗，重新取数。
- 异步请求携带发起时的账号上下文版本；切换后旧响应不得覆盖新账号页面。其他标签页发生切换时检测storage变化并刷新/暂停旧视图，不继续静默写入。

### 登录状态与错误

区分“未登录”“已识别人但未选账号”“账号可用”“账号失效”“服务暂不可用”。身份token存在不等于能进入业务页。

- 401：登录过期/凭据变更/另一个设备登录，清除认证并提示重新登录。登录表单本身的密码错误留在表单内处理。
- `ACCOUNT_REQUIRED`：进入账号选择；`ACCOUNT_UNAVAILABLE`：停止该账号操作、清理数据展示，重新获取可用账号，保留人的身份会话。
- 普通403：显示该操作无权或权益不足，不自动注销，也不自动切换到权限更高的账号。
- 503、超时、断网：显示暂不可用及重试，保留认证；受保护操作不降级放行，数据未知不显示为0。
- 退出先调用后端注销，再清本地。明确区分注销成功与仅本地退出；离线时不声称服务器会话已撤销。

暂保留三端现有独立storage key，不暗中建立共享登录。按人单设备意味着在另一个前端重新登录也可能使旧会话失效，需以三端测试验证并说明。共用登录或跨域跳转携带会话另行设计；本轮不在URL传token。

### 最小接口补齐

复用 `POST /api/auth/login`、`GET /api/auth/accounts`、`POST /api/auth/select-account`、`POST /api/auth/logout`、`GET /api/me`。平台是否采用 `admin-login` 的账号过滤，实施时与通用登录体验一致化。

建议在现有响应中补齐当前账号名、组织名、套餐、权益状态及业务能力，如开局、活动申请、组织管理、账号绑定、平台内容写入。能力由后端按已确认规则计算；它们帮助前端显示，真正请求仍由后端实时校验。无需为此建立通用策略引擎。现有 `validityValid` 只能表达部分付费状态，不能承担全部权限判断。

管理接口必须明确 `identityId`、`accountId`、`organizationId`、`subscriptionId` 的目标含义。列表、详情、统计、写入、导出逐项核查；不能仅替换URL或变量名后仍写旧 `users`。

## 4. 桌游玩家端

| 页面/区域 | 更新内容 | 行为边界 |
|---|---|---|
| 首页登录、顶栏 | 增加账号选择及切换；明确当前组织与账号；区分免费、体验、付费有效、付费到期 | 未选账号不发业务请求；到期仍可进入免费内容及历史 |
| 邀请注册 | 增加短信验证与请求编号；说明新手机号创建身份，已有手机号验证原密码后绑定账号 | 不覆盖已有姓名/等级；错误保留输入但不缓存密码或短信 |
| 完善资料、密码重置 | 资料仅编辑姓名/守望师名；密码走独立接口；修改密码后重新登录 | 资料保存不能把当前账号角色/组织覆盖为空；从完整上下文刷新 |
| 我的页面 | 分为个人资料、当前账号与权益、该账号历史/报告、账号切换 | 不按手机号合并A1/B3历史；不把NULL到期视为无限付费 |

| 报告、音频、文件、复盘 | 与当前账号历史一致；已有报告与新增收费处理区别展示 | 有历史访问权不等于可新增AI处理；下载仍走受保护接口 |
| 活动页、反馈、认证申请 | 核查字段切换状态，未接通时显示暂不可用并关闭提交 | 活动申请、认证流程未确认部分不虚构可用流程 |

游戏草稿以环境、身份、账号、场次区分；恢复前向后端校验场次访问和状态。旧草稿不能只凭旧 `userId` 推断账号归属，无法核实则提示不可恢复，不自动转给当前账号。

进行中或关键写入结果未确认时，建议暂停账号切换，提示“先完成或确认本局保存，再切换账号”。不新增“放弃场次”后台语义。后续若需要中途切换，另行明确保存、恢复和 pending 操作处理。

## 7. 写入恢复、缓存与交付顺序

网络超时可能发生在后端已提交之后。若前端每次点击重试都生成新编号，仍会重复开局或交付。因此一次用户操作固定一个 `requestId` 和请求体，收到明确结果后才结束；结果未知时提供确认/重试，不自动生成新操作。409不得静默改编号重发。注册重试还要核对短信一次性消费行为，不能照搬游戏重试逻辑。

只对开局、事件、结算、注册、套餐交付、续费、绑定等必要操作接入该规则，不对所有HTTP调用强制加编号。跨账号切换不重放旧账号pending写入；敏感表单不持久化密码。缓存只用于体验，恢复和写入均再次由后端校验。

执行顺序：

1. **F1 契约与页面清单**：补齐能力响应、管理对象ID及未完成接口清单，确认新增交互建议；与WQT-006后端任务共同维护。
2. **F2 三端认证**：登录/选择/store/router/错误处理/账号切换先形成完整闭环，单账号、多账号、无可用账号均可验证。
3. **F3 玩家业务链**：注册、个人资料、草稿、开局到结算、历史/文件/AI及请求编号一起验证，避免登录已切换而写入仍旧模型。
4. **F4 平台交付链**：在新HTTP接口就绪后完成身份、组织账号、套餐、续费和绑定页面，暂停旧对象写入口。
5. **F5 组织管理链**：账号列表、历史只读、统计、邀请码与绑定；依赖管理员/活动边界的入口继续保持关闭。
6. **F6 三端联调与验收**：隔离PG/Redis、浏览器及移动端验证，产出页面截图、测试结果和未关闭项。

不新增独立前端权限框架。共有交互规范与契约统一，代码先在现有各端封装最小认证/请求模块；只有实际重复和差异可控时再提取共享包。

旧模型部署的页面不得强行请求新接口。发布前选定与后台一致的前端版本，若必须同时支持两模型，使用服务器提供的明确模型标识；不能通过接口失败猜测模式后降级到旧写接口。新增多账号/换绑数据之后，回退继续遵守WQT-006数据恢复边界，不能只回退页面。
