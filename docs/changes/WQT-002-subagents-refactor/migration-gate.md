# G-MIGRATION · 场次固定组织归属

状态：2026-09-12 需求方确认采用 M1–M4，授权隔离环境实现与验证。2026-09-12，仅完成代码盘点，未读取生产数据；未知场次数量和存量冲突数量尚无证据。本文不代表迁移已执行。

## 已确认，不重复审批

- Organization 就是 Tenant，沿用 organizations.id。
- 组织场次永久归创建时组织，人员转组织不转移历史场次。
- 该规则不规定数据保留期限，也不自动规定离职人员的访问权。

## 当前事实

game_sessions 只有 user_id，没有创建组织快照。组织列表、成员统计、dashboard 通过 users.enterprise_id 推导历史归属；人员变动后统计会跟着变化。

人员组织字段被直接覆盖，当前代码没有完整的成员归属变更历史。活动关联可作为人工线索，但关联接口缺少场次所有者/组织一致性校验，activity_sessions 也不记录关联时间。因此“参加过 A 的活动”不能自动证明“创建时属于 A”。不能仅按活动或当前成员关系自动回填。

## 已批准的业务策略

| 决策 | 建议规则 | 用户可见影响 |
|---|---|---|
| M1 存量无法证明归属 | 标记 legacy_unknown；只由平台指定负责人核实，普通组织查询及经营统计不计入；有可信外部记录并留审计证据后再确认 | 部分组织历史统计暂时减少；不会把记录误给新组织 |
| M2 新场次与个人场次 | 后端读取当前成员关系；有组织写 organization，无组织写 personal；客户端不能选择归属。NULL 不同时表示个人和未知 | 独立个人场次保留个人语义，后续加入组织不迁移旧场次 |
| M3 转组织后的访问 | 组织场次由原组织有权限的管理员访问；原创建者离开原组织后不能再访问该组织场次的明细、文件、复盘或继续写入；新组织不能访问。个人场次仍由本人访问；平台运营权限沿现有明确管理边界 | 人员离开组织后个人历史页不再展示原组织数据；组织保留历史 |
| M4 活动关联 | 两个不同组织的场次/活动拒绝关联；个人场次不直接加入组织活动；公共活动仅作为活动关联，不改变场次归属。公开活动码不能绕过场次明细权限 | 某些原来允许的扫码加入会被拒绝；跨组织共享后续独立设计 |

这四项是本轮新增业务决策，尤其 M1 会改变报表口径、M3 会收紧离职访问、M4 会改变扫码关联结果。批准这些策略不等于批准生产迁移或上线。

## 实施与验证方案

1. 先建立只读盘点入口，要求显式目标连接，输出聚合计数与歧义类别；不导出个人资料。生产盘点结果用于评估影响。
2. 增加 organization_id 与 ownership_kind（organization / personal / legacy_unknown）；外键与检查约束确保状态一致。不给存量默认写入当前用户组织。
3. 开局时在同一事务/一致性边界读取成员关系并写入快照，处理与转组织操作的并发；客户端时间戳不用于证明历史组织。普通写入不能修改快照，人工纠错使用单独审计流程。
4. 场次列表、详情、结算、事件、活动、组织统计、复盘文件与外部 AI 上下文采用一致范围校验。不能只改列表让详情仍越权。
5. 使用 A/B 组织、个人、未知归属和历史脏关联夹具验证：A 创建→转 B→归属仍 A；A/B 列表与统计对账；旧 JWT、离职访问、跨组织关联、重复迁移与并发操作。
6. 先在隔离 PG 演练增量迁移、约束与回退，再提交生产影响清单、备份和恢复证据。应用回滚保留新字段与归属数据，不能回到按当前用户组织开放访问的旧查询；生产部署作为独立 gate。
