# G-AUTH · 管理身份不能绕过租户校验

状态：需求方于 2026-09-12 确认“采用完整验证，纳入本轮隔离实现”。2026-09-12 代码审查发现；未尝试访问线上系统。

## 具体问题

现有 /api/auth/admin-login 只检查手机号属于 boss/operator，就签发管理 token，不校验密码或验证码。/api/auth/dev-login 使用共享开发密钥，数据库种子与代码均有公开默认值。/api/settings 返回全部配置，可能包括该密钥。这些入口在 [auth.routes.js](../../../src/routes/auth.routes.js)、[db.js](../../../src/db.js)、[settings/routes.js](../../../src/platform/settings/routes.js) 可复核。

因此即使场次 SQL 全部按组织过滤，冒用平台身份仍可绕过租户边界。这是现有行为，保持行为重构没有引入该问题；不能把保留漏洞当作租户安全验收通过。

## 可实施的建议

1. 管理端统一走现有 /api/auth/login 的手机号、密码、短信验证码及单设备会话流程；登录成功后再按数据库实时角色进入管理页面。
2. 删除手机号即发 token 的路径；如保留 /api/auth/admin-login 兼容地址，必须调用同一完整验证流程，并增加管理角色要求。
3. 默认关闭 /api/auth/dev-login；只有显式开发环境开关及非默认、环境注入密钥同时满足时才允许使用。禁止数据库公开种子作为登录凭据。
4. /api/settings 只返回玩家 UI 明确需要的公开配置白名单；管理配置保留现有 boss 专用入口。
5. 补负向测试：知道管理员手机号或公开旧密钥仍无法登录；撤销平台角色后旧 token 无权限；完整验证成功后正常进入管理端。

## 影响与责任

管理人员需要可用密码与短信验证；现有只输入开发密钥的后台登录页需要同步更改。隔离测试使用短信替身，不发送真实短信。上线前必须确认实际管理账号与短信配置可用，不能先关闭旧入口导致团队无法登录。

本轮按已确认策略完成隔离实现与验证；生产切换仍放在发布 gate。管理端本来已有完整手机号登录表单，本轮移除开发密钥备用页；不新增另一套认证产品。
