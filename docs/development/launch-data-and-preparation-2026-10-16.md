# 香港临时上线：数据决策与部署准备

日期：2026-10-16。状态：工作稿、未提交。关联：[只读核查与容量证据](launch-readiness-2026-10-16.md)、[领域规则](../architecture/domain-rules.md)、[WQT-006](../changes/WQT-006-account-permissions/spec.md)、[旧版当前发布记录](../changes/WQT-007-download-center/release.md)。

## 已确认和待决定

需求方本轮确认计分端＋平台管理端；旧香港服务器同机隔离；旧版与 www 继续运行；旧版历史数据备案后迁移；容量先按同时 10 桌准备。另一会话完成代码后，需求方再确认候选基线。本次不修改该会话业务文件，不构建正在变化的工作区，不导入/迁移正式数据。

独立库和服务的隔离方向已获确认，不重复审批。需求方追加确认：首批仅团队和新客户；默认卡牌为2026年新版，保留每场开局选择卡组；平台管理员为团队全员。旧客户承接不阻塞本次部署，见[老客户处理清单](legacy-customer-follow-up-2026-10-16.md)。团队具体手机号通过受控名单核对，不从所有旧用户或所有组织成员推断团队身份。未据本文件创建付费资源、修改云端配置或生成正式账号。

## 数据不只有历史场次

即使旧历史全部延期，新版仍需要三组数据：能够登录和授权的账号组织数据；决定玩法和得分的卡牌配置；支持短信、文件与 AI 的运行配置。空数据库能建出表，不代表能完成真实业务。

以下是代码级逻辑清单，不是生产逐表盘点。本次没有读取客户手机号、密码摘要、历史文本或云端密钥值，未给未经核实的存量数量。

| 数据类别 / 当前制品 | 今天是否需要 | 推荐处理 | 主要风险与验收 |
|---|---|---|---|
| 组织 organizations | 首批正式组织需要 | 创建确认清单内组织，名称/地点/归属负责人核对；通用组织 0 由账号迁移初始化 | 同名不是同一租户，不能按名称自动合并旧组织 |
| 登录身份 identities | 首个管理员及首批用户需要 | 首个管理员受控初始化；其余以正式短信验证和邀请建立身份 | 手机号只表示当前登录身份，不自动证明旧权益或历史所有权；不得复制演示密码 |
| 业务账号 accounts、account_bindings | 需要 | 为正式人员分配明确角色和组织；其余走邀请绑定 | 身份与账号是两套 ID；boss 平台权限需指定人员，不能照搬旧 users.role |
| 套餐 subscriptions、账号期限 | 有付费/正式交付用户时需要 | 依已确认交付清单建立个人/团队/城市套餐、数量和准确截止时间 | 重新交付不能无意重置旧合同期限、换绑次数；不确定权益暂不发放，不能用体验冒充已购权益 |
| 体验、守望者等级 | 视首批用户情况 | 新用户按现行规则；旧用户等级/体验已用状态若需沿用，单列受控映射 | 重建旧用户可能重复赠送体验、等级丢失，延期历史迁移不代表允许权益重置 |
| 邀请码 invite_codes | 推荐需要 | 生成新版专用、限定组织/次数/有效期的邀请码 | 不复制旧邀请码，避免旧码在两套系统重复消耗；邀请码不进入公开仓库 |
| 已发布卡牌 cards_released、卡组 card_groups | 必需 | 导入经产品指定的正式发布快照与卡组，明确唯一默认卡组 | 卡组存发布快照 ID；不能只拷贝卡牌正文或重编号而不改引用；校验各阶段数量、选项效果及评分上限 |
| 卡牌编辑 cards、card_versions | 今天要编辑/发布卡牌才需要完整带入 | 只计分可先导入所需正式内容；今天要运营编辑则连同选定卡牌的版本链一起迁入 | author_id 与 author_identity_id 不同命名空间，旧作者不能因数字相同获得新版权限 |
| 卡牌图片/音频等静态素材 | 被正式卡牌引用时需要 | 列出引用清单与授权；必要素材复制到新版资源边界，或经确认只读引用旧正式素材 | 正文正确但音频 URL 失效也会影响使用；旧素材删除会影响新站，不能依赖未经确认的存续 |
| 游戏模式、评分、品牌配置 system_settings 的非敏感部分 | 必需 | 按键白名单核对玩法、模式、时长、伍力规则、复盘阈值、自助注册和品牌文本 | 不整表复制；数据库非空配置可能覆盖环境变量，不能把旧连接/权限带入新环境 |
| 短信、人机验证、OSS、AI 配置 | 对应功能需要 | 新版独立凭据/权限及费用统计；逐功能验证，不复制旧数据库密文 | 缺配置可能拒绝启动；密文与旧加密密钥绑定；生产密码登录当前要求人机验证 |
| 历史场次 game_sessions、事件 game_events | 本轮不迁移 | 留在旧版，旧版继续查询；新版从自己的首场开始记录 | 场次永久归创建组织；未来导入保留旧来源和 ID 映射，不能用当前人员所属组织补历史 |
| 历史活动 activities、关联 activity_sessions | 本轮不迁移 | 首期活动若需要则在新版正式新建 | 不跨系统拼接活动统计，旧活动码不自动赋予新版访问权 |
| 场次文件 session_files、录音、复盘报告 | 历史延期；新版上传需要存储 | 历史保持旧引用，新文件写入新版专用边界 | metadata 与对象必须成对迁移和恢复；不能只备份数据库或公开旧私有对象 |
| 反馈、等级申请/审核记录、组织运营记录 | 历史延期 | 旧版保留，新版新增独立留痕 | 未结审批若要承接需专门清单，不能默认丢失或自动审核通过 |
| 下载资料 download_releases、download_events | 目录今天开放才需要正式资料 | 由平台正式上传，保留版本、对象键、SHA-256；旧审计不复制 | 新版目录先为空必须明确展示；下载次数属于各系统自己的审计 |
| Redis 登录会话、验证码、用户会话、幂等记录 | 新版运行需要新生成 | Redis 从空命名空间开始；旧 token/验证码不导入；新业务操作记录由新版产生 | Redis 不可用会拒绝认证；不能从陈旧 Redis 备份复活已撤销会话，故障后必要时强制重新登录 |
| 演示组织、虚构用户、测试场次/验收文件 | 不需要 | 全部排除 | 正式库为空不代表能直接导入演示 seed；测试工具不作为生产初始化入口 |

## 推荐的数据方案

推荐“新版独立起步＋小批量正式开通＋正式卡牌快照”，旧历史迁移延期。它不是整个旧库清空重来：已购权益、等级和已消耗体验仍须明确是否承接；若首批包含旧客户，则只对这些人的身份/组织/权益做经确认的映射和对账，不复制其历史场次。

| 选择 | 优点 | 代价 | 建议 |
|---|---|---|---|
| 完全新开通，首批仅内部/新用户 | 不依赖旧客户映射，最快形成干净的新库 | 旧客户暂不承接历史与已有权益，需明确使用说明 | 今天先内部/新用户试用时优先 |
| 首批旧客户的最小身份与权益承接 | 老客户可用新版，同时保留商业交付连续性 | 需要确认人员、组织、套餐剩余期限、等级、体验状态和绑定映射 | 今天必须服务老客户时推荐；这是小范围迁移，仍要审阅与对账 |
| 整库复制再运行新版迁移 | 表面上已有数据都在 | 把旧组织归属、身份映射、密文、旧会话等风险一次带入，和历史延期目标冲突 | 本轮不建议 |

**本次已确认的数据决定：**

1. 首批只服务团队和新客户，并发目标10桌；旧客户继续在旧版使用，身份/权益承接上线后另做，不阻塞首批。
2. 默认使用2026年新版卡组；开局预设仍可选择其他已正式发布并导入的卡组，不强制每场使用默认组。最终发布时固定实际2026快照/卡组及素材，名称本身不保证版本相同。
3. 团队全员拥有平台管理员权限；受控核对团队名单后逐人建立身份和boss账号，不使用共享密码或演示账号。首个管理员初始化后，其余团队成员按正式绑定流程开通。
4. 旧客户的套餐、等级、体验和绑定映射均移到独立后续清单；不在本次部署中默认重置或承接。

**代码核对：**public/player/player.js 的开局预设有“卡牌组”下拉，按 is_default 预选；/api/player/start 要求有效 cardGroupId，写入场次时保存卡组名称和 releasedIds 快照。恢复场次优先读取该快照。因此默认2026与每场选择并不矛盾，修改默认组不应改动已开场次的选牌。当前平台活动实体不是统一卡组模板：活动关联用于组织范围与桌号；实际卡组在每桌开局预设中选择。若未来要求活动下所有桌强制同卡组，属于另一项需求，本次不推导。

文件隔离本轮推荐新私有 bucket＋独立最小权限凭据。若因预算或迁移选择同 bucket 前缀，必须逐条验证写入、列举、读取、删除权限和对象键覆盖；当前 sessionFileObjectKey 固定为 session-files/<sessionId>/<uuid>，不能仅配置一个“前缀变量”就声称隔离。当前 CSP 图片/音频白名单固定旧桶域名，使用新素材域名需要在候选基线冻结后同步适配并验证。该选择属于已确认隔离方向的落地设计，不改变旧桶 ACL 或旧对象。

## 现有代码的初始化约束

- src/runtime.js：card_groups 为空会读取 public/cards-data.js，生成“初版卡牌”发布快照和默认组；不会自动复制旧站最新发布版。正式导入顺序须设计为一次初始化并校验默认组，避免启动自动 seed 与正式导入叠加。
- src/db.js：建表、配置默认值、执行账号/游戏等迁移；src/runtime.js 还会清理过期场次。不能用“启动看看”盘点旧库。
- src/db/migrations/accounts.js：通用组织 0、身份/业务账号分离、账号所属组织和场次创建人约束；没有正式首个 boss 的安全 bootstrap。现有 tests/helpers 是验收/演示工具，禁止照搬到生产。
- src/services/identity-sessions.js：身份会话存 Redis，同一身份新登录替换旧会话。scoring/admin 子域不共享 localStorage，同一手机号在两端分别登录会使先前会话失效；这是当前规则的跨子域表现，最终 UAT 必须覆盖，不擅自改成跨端多会话或跨域 token 传递。
- src/sql-pg.js：每个连接池上限 10；主库、卡牌库各自建池。新 PG 若承载两个逻辑库，要按至多 20 个应用连接加管理/备份连接核算，不按“一个 Node 实例只有一个连接”估算。
- 组织端不发布不等于只隐藏导航：当前 Express 仍会托管 /enterprise/。发布入口策略要对不在范围的页面明确拒绝/不托管，保留计分端与平台需要的 API；不凭 Host 或前端隐藏替代后端角色授权。

## 服务器容量与可先完成的准备

近 24 小时实测数据见核查文档：CPU 峰值约 8%，内存历史峰值约 49%，磁盘约 27%；即时内存余量约为 status 的 1825/3563。服务级近 12 小时已取样，不将服务进程读数相加替代整机用量（系统、容器运行时和缓存另占资源）。当前负载明显偏低，尚无新版真实业务并发证据。

计划保持旧项目不变，在同台机器建立独立新版项目及单实例 Node、新 PostgreSQL 18 服务和 Redis；主库与卡牌库可在这个新版 PG 内分逻辑库/角色，和旧 PG 无连接复用。无需为了两个前端引入三个 Node 进程。资源预算先按新版整套稳定工作集约 1 GiB 的验证目标，给系统和旧站留出约 0.7 GiB 余量；这是待测预算，不是容量承诺或已设置的容器限制。

前端构建及镜像制作优先在 CI/构建机完成，避免在服务旧业务的机器上同时做多次构建。候选容器总内存必须覆盖 Node 堆、原生 Buffer、文件上传及报告处理；只限制堆大小不能限制整机内存。当前单文件上限 50 MiB、上传会读入内存，多个上传会叠加，不用低频登录的内存消耗代表高峰。

本轮已完成：只读服务器/服务指标取样、轻量旧站 HTTP 探测、数据依赖清单、配置清单、执行顺序与回退约束。尚未创建新版云资源：候选版本、数据输入和凭据未齐备；离线 staging 不自动续费或删除。没有向线上发压力流量。

## 基线确认后的执行顺序

1. 需求方确认另一会话完成的准确 SHA、上线范围；本稿数据选择按上述确认执行；汇总受影响技术检查和已有产品验收，缺少的计分端验收补齐。
2. 完成正式数据 manifest：来源版本/时间、组织与管理员清单、卡牌数量/卡组引用/默认组、配置白名单、文件引用、排除项和校验摘要。手机号和密钥只在受控位置保存。
3. 创建同机独立空资源、私有网络/权限和备份目标，注入专用凭据；只读核对连接目标后再初始化新版空库。不开启 Git push 自动部署。
4. 初始化首个正式管理员和正式内容；核对组织角色、卡牌引用与默认组、计分规则和素材；备份初始化后数据库并在独立恢复目标验证。备份同时覆盖卡牌库、对象清单和必要密钥托管。
5. 使用隔离验证入口进行真实认证、开局/事件/结算/复盘、文件、跨组织拒绝、Redis 断开与重启验证。先用合成无敏感内容，精确清理本轮创建数据；不能在将收正式数据的库里遗留测试账号。
6. 按需求方确认的同时 10 桌，在新版隔离入口逐级加压（1→5→10 个独立活跃场次；10 桌持续至少 30 分钟，覆盖开局、事件和集中结算，叠加 2 个管理端读操作客户端及 1 路合成文件上传）。桌数按独立活跃场次计，不用 10 次串行 HTTP 冒充 10 桌；按最终客户端真实事件频率构造负载，记录延迟、错误、重复写入和资源峰值，不临时发明替代现有标准的延迟阈值。观察整机、新版及旧站。初始建议停止条件：旧站轻量探测连续 3 次失败、整机内存达到 80%并持续 2 分钟、CPU 达到 80%并持续 2 分钟、任何 OOM/数据库连接耗尽/错误写入。停止条件是拟定运行保护，不是降低已有 vNext 容量验收基线；如本次是范围更小的首批上线，应由需求方明确范围并关联原门槛差异。
7. 通过业务验收及发布 gate 后绑定新域名/证书，核对新旧域名分别命中正确版本，记录实际 SHA/镜像和新库标识；只开放 scoring/admin，旧 www 不切换。
8. 初期持续观察错误、内存、磁盘增长和备份结果；告警接收人与响应责任落实。出现问题停止新版入口/写入并保留新版数据，不回写旧库，不以旧库备份覆盖新版增量。

不将新版应用回退到 legacy 模式运行新账号库。代码回退只能选择已验证兼容新版 schema/数据的版本；尚无兼容版本时，优先维护页＋保留数据再修复，不能宣称“随时回滚”。旧站现有安全回退 SHA 见 WQT-007，只适用于旧站。

## 备份与后续搬迁

10 月 13 日旧版记录有同卷归档，不能抵御香港机器/磁盘整体丢失。新版第一条正式写入前，需要需求方明确数据损失窗口与恢复时间，再落实异机私有备份频率、保留期和独立恢复证据。可讨论的目标：最多丢失 1 小时数据、4 小时内恢复；当前尚未测得恢复耗时，也未承诺满足。数据库恢复必须与对象版本/文件清单对齐，Redis 会话可撤销后重建。

后续搬迁拆成两件事：新版库和对象搬到备案后的服务器；旧历史按独立迁移规则导入。迁移记录保留 source_system、旧实体键到新实体键的映射与核对结果（具体 schema 待迁移设计，不提前新增通用框架）。相同手机号和组织名称只作为核对线索，不能触发自动合并。新旧并行期间场次各自只记一次，活动统计不跨库拼接。
