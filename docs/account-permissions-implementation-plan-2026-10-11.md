# WQT 账号权益与权限改造执行方案

更新日期：2026年10月11日

**核心关系：组织拥有账号，账号绑定具体的人。场次归产生它的账号。管理员权限是账号属性，免费账号也属于组织。**

本版按最新讨论重写，替代之前执行方案及其 Word 版本。之前把“账号”当成“人”，由此推导出的“一个账号加入多个组织”“换绑给另一个账号”均作废。

这是一份执行中的代码改造方案，已吸收critic审查及后续决定。本session正在独立分支实现与隔离验证，整体改造、生产迁移和部署尚未完成，最新范围与证据见[WQT-006变更制品](changes/WQT-006-account-permissions/spec.md)。先行生产操作是已有记录：创建公司自用“伍仟天”组织，纳入需求方指定的4个账号，并按明确指令把其中原普通用户提升为boss。具体数据库证据与当前限制见第9节，不代表新架构已经部署。

## 1 先用一个例子说明

A组织购买小组级套餐，拥有5个账号：A1、A2、A3、A4、A5。

B组织购买城市级套餐，拥有20个账号：B1至B20。

张老师的手机号同时绑定A1和B3。张老师登录后，可以选择使用A1或B3，但A1始终属于A组织，B3始终属于B组织。一个人可以进入多个组织，是因为他绑定了不同组织的账号，不是一个账号拥有多个组织。

张老师使用A1开展的游戏，场次归A1；使用B3开展的游戏，场次归B3。不能因为手机号相同，就把A1的历史计入B组织。

A1以后换绑李老师的手机号，变化的是使用A1的人。A1没有被删除、重建或转给B组织，其剩余期限和历史场次仍留在A1。李老师能否查看换绑前的场次，需要单独确定访问规则；张老师不再因旧绑定获得A1的访问权。

个人级也是同一结构：一个组织拥有1个账号，这个账号绑定购买者。个人级与小组级不开放组织管理接口，但数据库里仍然有组织。

## 2 已确认的业务规则

### 组织 账号 人

- 组织拥有一定数量的账号；一个账号属于一个组织。
- 手机号、微信等用于识别具体的人，不作为账号本身的定义。
- 同一个人可以绑定不同组织的账号，也可以使用自己购买的个人级账号。
- 账号可以换绑使用者，换绑不改变账号所属组织、期限和场次归属。
- 管理员权限是账号属性，管理员属于组织拥有的账号之一。一个组织可以有多个管理员账号，不建立脱离账号的个人管理员权限。
- 账号换绑保留账号角色。新使用者使用该账号时具有该账号权限，旧使用者失去该账号权限；管理员账号换绑必须经过相应授权。
- 多账号登录必须选择本次使用的账号，只有一个账号时可直接进入。
- 免费注册也有账号：通用邀请码的组织ID为0，目标归入通用组织，也称免费组织。
- 公司自己使用的账号纳入公司自己的生产组织，不长期保持无组织绑定；该组织与免费组织0分开。
- boss负责平台管理；本次目标不需要operator层。已有operator不能自动升级为boss或直接删除。

### 套餐与续费

| 套餐 | 组织拥有的账号数量 | 管理规则 | 已明确期限 |
| --- | --- | --- | --- |
| 个人级 2000元 | 1个 | 无组织管理员 | 首次购买1年，每次续费1年 |
| 小组级 7500元 | 5个 | 无组织管理员，账号分配与换绑由平台处理 | 首次购买1年，每次续费1年 |
| 城市级 | 20个 | 有组织管理员和自动运营能力，具体操作范围待定 | 每次续费1年，首次购买期限和价格待明确 |

- 购买套餐创建组织，并提供对应数量的账号。
- 同一套餐统一到期；提前续费从原到期日增加一年。
- 换绑后的使用者继续使用原账号的剩余期限，不重新计算一年。
- 每份套餐终身共允许两次换绑。小组级、城市级是整份套餐共两次，不是每个账号各两次；续费不重置次数。
- 建议续费复用原组织和账号。重复购买、升级是否新建组织，以及过期后从哪天续期，仍需明确。

### 免费与体验

- 免费状态可以登录并使用免费内容。
- 体验期从首次激活开始一个月，期间可凭有效活动码开局。
- 体验结束自动回到免费状态。
- 付费有效时，可使用对应付费能力，包括申请活动；申请流程还需明确。
- 免费账号来源已明确：通过邀请码注册，组织邀请码归对应组织，通用邀请码归免费组织0。体验资格按人还是账号计算仍需确认。

微信绑定在国内服务器完成备案、具备微信API对接条件后开发。本轮先实现手机号身份，不接入微信。

## 3 当前系统的问题在哪里

当前users表同时保存手机号、密码、role、enterprise_id和valid_until，场次通过game_sessions.user_id关联它。系统把“登录的人”和“被组织拥有的账号”放在了同一条记录里。

| 当前代码 | 改造方向 |
| --- | --- |
| 用手机号查询唯一users记录后直接登录 | 先识别人，再查询这个人当前绑定的账号 |
| users.enterprise_id表示所属组织 | 组织归属保留在账号上；不能改成账号加入多个组织 |
| role写在混合了人与账号的users记录上 | 明确为业务账号属性，不作为人的全局身份 |
| 同一手机号只能找到一个业务账号 | 同一手机号对应一个人，这个人可绑定多个业务账号 |
| 会员到期同时阻止登录 | 人仍可登录免费内容；收费行为按所选账号检查权益 |
| 会话里的uid同时表示登录者和业务账号 | 区分登录的人与本次操作的账号，并实时检查绑定 |
| 场次读取依赖当前用户组织和ownership_kind | 场次归稳定的账号，组织信息不能替代账号访问校验 |
| 通用邀请码注册实际写入enterprise_id为NULL | 目标归免费组织0，补齐真实组织记录和0值判断 |

手机号唯一不是需要删除的约束：它可以继续用于防止创建重复的手机号身份。需要改变的是手机号身份与业务账号之间的关系。

部分卡牌管理接口只检查登录，没有检查管理员角色。开放免费登录前必须修复，否则免费登录者也可能调用发布、删除等管理操作。

免费组织0是已确认目标，当前实现尚有差异：src/routes/auth.routes.js只有`invite.type === "organization" && invite.organization_id`成立才绑定组织，0会被跳过并写NULL；邀请码生成也用真假值判断。源码中没有发现创建组织0的初始化；本次生产只读核查也未发现组织0记录。这次没有创建免费组织0或修改注册接口。

不能只把NULL批量改为0。需要建立或核实真实组织0，显式区分0与NULL，检查注册、外键、列表、活动关联和统计。免费组织不套用付费有效期封禁；不同免费账号不能因同属组织0而互看历史。

## 4 数据应怎样分开记录

下列是建议的数据职责和表名。保留现有Express与PostgreSQL单体，不需要为这次改造拆多个服务。

| 记录 | 保存什么 | 关键关系 |
| --- | --- | --- |
| 组织 organizations | 名称、组织状态 | 一个组织拥有多个账号 |
| 账号 accounts | 稳定账号ID、所属组织、账号状态、角色 | 管理员是组织账号之一，权限来自所选账号 |
| 人 identities | 稳定身份ID、手机号、登录资料、身份状态 | 同一个人可绑定多个账号 |
| 账号绑定 account_bindings | 哪个账号由哪个人使用、开始和结束时间 | 保存当前绑定及换绑历史 |
| 套餐 subscriptions | 稳定权益ID、组织、档次、账号数量、日期、已换绑次数 | 账号明确关联适用权益；续费不重建计数 |
| 场次 game_sessions | 产生场次的account_id、游戏记录 | 不因手机号换绑而换所有者 |

建议一个账号同时只有一个有效使用者，换绑结束旧绑定并建立新绑定。多人共享同一账号不在当前已确认范围内；同一人是否可以绑定同一组织的多个账号也需明确。

身份停用、账号停用、组织停用是三个不同操作。停用一个账号，不应自动停用这个人绑定的其他账号；组织停用影响哪些操作，要明确规则后实现。

手机号变更也有两种情况：同一个人换手机号码，只更新身份联系方式；账号从张老师换给李老师，才是换绑使用者。验证方式与是否扣换绑次数需要确认，不能把每次修改手机号都当成换人，也不能让“改手机号”绕过换绑限额。

身份登录凭证建议保存在人的记录上。账号保留业务数据，避免新使用者继承旧使用者的密码、微信身份或个人资料。未来微信与手机号如何合并为同一个人，届时再定义，不仅凭字符串相同自动合并。

### 管理权限属于账号

需求方已确认组织管理员是账号属性，不再保留“给人还是给账号”的分支。A1是A管理员，张老师使用B3时不能带入A1管理权。账号换绑保留角色，新使用者获得该账号权限，因此换绑管理员账号的授权必须受控并留记录。

公司现有boss不能因为纳入公司组织被降成enterprise；管理员属于组织账号之一，不另外建立“不占账号的管理员身份”。

补充字段归属清单：姓名、联系方式和密码属于人；角色、权益和场次归属属于账号。活动创建人、上传人、反馈作者记录实际操作者，不能机械地把所有user_id改成account_id。认证等级等按业务另定。

免费组织和公司组织可以拥有账号而没有商业套餐，不凭组织存在就假定付费或豁免。分别明确账号、组织和人的状态影响。

## 5 登录和每次操作怎么执行

1. 用手机号及现有登录验证方式识别这个人，建立人的登录会话。
2. 查询这个人当前有效绑定的账号，显示账号名称、所属组织和期限。
3. 人选择本次使用哪个账号，例如A1或B3。只有一个账号时可直接进入，多个账号提供切换。
4. 后端核实这个人仍绑定所选账号；前端传account_id不等于有权限。
5. 根据所选账号检查账号状态、所属组织状态、套餐权益和本次行为权限。
6. 创建场次时由后端写入所选账号ID，不能由客户端指定任意场次所有者。

选择A1开局后，这个场次一直按A1检查。切换到B3不能把正在进行的A1场次写成B3，也不能因为页面缓存了A1就绕过已撤销的绑定。

换绑完成后，旧使用者的后续A1请求必须被拒绝，包括旧凭证、已打开的页面和文件下载。旧使用者仍绑定B3时，可以继续使用B3，不必把整个人的所有登录和账号一并撤销。

| 行为 | 后端检查 |
| --- | --- |
| 登录和免费内容 | 人和绑定账号状态正常，登录有效；免费账号属于组织0，不要求付费 |
| 开局或申请活动 | 当前账号绑定有效、状态允许、具备对应权益 |
| 体验凭活动码开局 | 体验有效、活动有效、允许参加、使用账号合法 |
| 读取场次和报告 | 场次归哪个账号、当前人对该账号有哪些访问权限 |
| 组织管理 | 所选账号有管理员属性，操作目标是其所属组织，组织开放管理能力 |
| 平台管理 | 所选账号保有boss权限，检查具体操作并记录必要审计 |

账号属于组织不等于组织管理员可以无限操作所有历史。管理员能否看账号全部场次、换绑后新使用者能否看历史、免费或到期能否下载报告，仍要确认。

### 登录有效期

已提出同设备24小时后重新登录。建议从人的登录时间计算，切换账号不重新开始24小时；这个细节仍需确认。原来的“单设备”限制也要明确按人还是账号计算。

每次请求轮换Tn会出现并行冲突：页面两个请求都带Tn，第一个更新后第二个就被误判失效。建议使用稳定会话标识并实时检查会话与账号绑定，而不是每请求轮换；这个建议尚未确认替代原Tn要求。

Redis的职责、故障处理和恢复方式单独确定。即使用Redis存登录会话，账号、套餐、绑定和场次仍以数据库为准。不能仅靠会话里缓存的旧绑定放行请求。

## 6 按什么顺序修改代码

### 第一步 固定规则并核对权限缺口

先形成版本化需求、实施计划和验证记录。同步领域规则、vNext基线和AGENTS.md中的旧归属说明，保留决定来源。本轮不是把账号改成多组织成员，而是把账号与人拆开。

检查管理写接口，补齐卡牌发布和删除等权限，再开放免费登录。主要代码：src/game/cards/routes.js、src/middleware/rbac.js和各管理路由。

完成标准：文档与实现目标一致；普通登录者不能调用平台管理操作。

### 第二步 准备基础组织和人账号映射

公司自用生产组织已创建并纳入指定成员，具体证据见第9节；不把全部NULL组织账号当成自己人。免费组织0单独初始化并改注册与权益校验，避免重复和误归类。

增加迁移，分开账号与登录身份，采用accounts、identities和account_bindings表达目标模型。需求方说明旧数据简单，优先使用旧账号到新账号的一对一清单，仅做一次轻量异常核查；场次留在开展它的账号上，不预建复杂历史拆分机制。

组织账号归属继续是一对多。不要建立“账号加入多个组织”的表来替代enterprise_id。同一人通过绑定多个账号进入不同组织。

主要代码：src/db.js、src/db/migrations、账号与身份查询模块。

完成标准：A拥有5个账号，B拥有20个；张老师绑定A1和B3；A1仍只有一个所属组织；账号可以尚未绑定使用者而存在。

### 第三步 整体切换登录 账号选择和场次访问

登录先返回人的身份，再提供当前可用账号列表和选择入口。把现有req.user.uid的用途逐一检查，区分identity_id和account_id。保护所有收费和数据接口，后端实时核验绑定，不只靠JWT中的旧信息。

账号选择、开局、写事件、结算、历史列表、报告和文件访问作为一个受控切换单元交付，不能先换登录ID最后再换场次ID。新增表可以先部署，切换前旧请求链保持原行为。

主要代码：src/routes/auth.routes.js、src/middleware/auth.js、src/services/sessions.js、src/platform/access/session-scope.js、src/game/sessions/service.js、src/platform/identity/profile.routes.js、src/integrations/media/session-files.js及三个前端的登录状态与请求处理。

完成标准：同一手机号能选择A1和B3；不能选择未绑定的A2；换绑后张老师的旧请求不能再操作A1；B3仍可使用；切换账号不会把场次写到别的账号。

### 第四步 实现套餐交付 续费和换绑

购买创建组织、套餐和对应数量的稳定账号，之后把账号绑定给人。小组级绑定和换绑由平台操作；个人级与城市级操作主体确认后再开放相关入口。

换绑必须在同一次数据库事务里核验权限与剩余次数、结束旧绑定、建立新绑定、扣次数和保存操作记录。否则两个同时发来的请求都可能看到“还剩一次”，实际换绑两次。同一次购买或续费重复提交只能交付一次。

同一事务还要配合数据库保护：锁定套餐记录或按剩余次数原子更新，当前有效绑定建立唯一约束；换绑与业务写操作协调同一账号锁，写入时再核验绑定。购买、续费以唯一业务请求号避免重复交付，验证最后一次换绑只有一个请求成功。

主要代码：新增套餐和绑定业务模块、src/db/migrations、src/routes/account-admin.routes.js、admin-web/src。先做平台录入还是同时接支付渠道，另行确定范围。

完成标准：购买生成1、5、20个账号；空绑定不删除账号；整份套餐第三次换绑拒绝；换绑不新建账号、不改期限、不移动场次；续费不重置次数。

### 第五步 调整权益和管理权限

按确认后的对象记录免费与体验资格，首次激活不被重复延长。付费行为检查当前所选账号的套餐，不把同一个人另一个账号的付费状态直接搬过来。

个人级与小组级没有组织管理接口权限；城市级按确定的授权方式允许多名管理员。没有付费权益的人仍能登录免费内容。

通用邀请码注册显式生成组织0中的免费账号。组织邀请码分配该组织合法的空闲账号，不超过购买数量；已注册手机号复用人的身份。免费组织不套用商业套餐名额与到期封禁，但邀请码使用次数和注册防滥用仍受控。

主要代码：src/account.js、src/middleware/rbac.js、src/platform/organizations/routes.js、src/game/activities/link.js、enterprise-panel/src。

完成标准：体验结束回到免费；A组织管理员不能管理B；同一个人使用A1和B3时分别得到各自权限与数据；角色授权不会因换绑被意外转交。

### 第六步 完成组织统计和全量验证

第三步已经整体切换场次、报告和文件访问，本步补组织统计、展示与全量回归。场次按稳定account_id关联，真实操作者另记，不能拿登录identity_id代替账号ID。

## 8 开发前仍需决定的边界

1. **管理员具体行为。** 权限属于账号已经确认；仍需明确任命和撤销同级、最后一名管理员保护、管理员账号换绑由谁批准。

3. **体验资格归谁。** 免费账号来源已确定为邀请码注册并归免费组织0；体验按人还是账号、换绑或多账号能否再次体验、自然月还是30天仍需明确。

6. **停用和到期的行为。** 人、账号、组织分别停用后影响什么？付费到期能否读历史和下载报告，进行中的场次能否结算？
7. **登录会话方式。** 24小时从何时起算，单设备按人还是账号；是否接受稳定会话替代Tn轮换；Redis故障和恢复如何处理？
8. **活动与自动运营。** 活动申请审批、参加资格、组织统计范围；自动运营可以执行哪些操作，哪些需要人工确认？
